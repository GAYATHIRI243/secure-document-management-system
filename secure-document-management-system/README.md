# Secure Document Management System
### with Real-Time User Behavior Monitoring and Risk Detection

A full-stack MERN application for securely storing documents while continuously
scoring user behavior for risk, in real time.

## 3. Prerequisites

- Node.js 18+ and npm
- MongoDB running locally, or a MongoDB Atlas connection string

### MongoDB setup

**Option A — Local MongoDB**
```bash
# macOS (Homebrew)
brew tap mongodb/brew
brew install mongodb-community
brew services start mongodb-community

# Ubuntu/Debian
sudo apt-get install -y mongodb
sudo systemctl start mongod
```
Your connection string will be: `mongodb://127.0.0.1:27017/sdms`

**Option B — MongoDB Atlas**
1. Create a free cluster at https://www.mongodb.com/atlas
2. Create a database user and allow your IP
3. Copy the connection string into `MONGO_URI` in `backend/.env`

## 4. Backend setup

```bash
cd backend
npm install
cp .env.example .env
```

Edit `.env` and set at minimum:
```
MONGO_URI=mongodb://127.0.0.1:27017/sdms
JWT_SECRET=some_long_random_string
CLIENT_URL=http://localhost:5173
```

Create a default administrator account:
```bash
npm run seed
```
This prints the admin credentials:
```
email:    admin@sdms.local
password: Admin@123
```
Change this password after your first login (edit the user via the User Management page, or update it directly in the database).

Run the backend:
```bash
npm run dev     # with nodemon (auto-restart)
# or
npm start       # plain node
```
The API runs on `http://localhost:5000` by default. Check health at
`http://localhost:5000/api/health`.

## 6. Using the app

1. Visit `http://localhost:5173` → Landing page
2. Log in as the seeded admin (`admin@sdms.local` / `Admin@123`), or register a
   new normal-user account
3. As a normal user: upload documents, view your activity, check your risk score
4. As an admin: open **Live Monitoring** in one tab and, in another
   browser/incognito window, log in as a user and upload a file, or fail a
   login a few times — you'll see the activity and risk score update live in
   the admin tab via Socket.IO
5. Trigger a security alert: log in with the wrong password 3+ times within
   15 minutes for a given account — a "Multiple Failed Logins" alert is
   generated automatically and streamed to the admin's alert page

## 7. How risk scoring works

Implemented in `backend/services/riskService.js`:

| Event                          | Points | Trigger condition                                  |
|---------------------------------|--------|-----------------------------------------------------|
| Failed login                    | +10    | Every failed login attempt                          |
| Multiple failed logins          | +25    | 3+ failed logins within 15 minutes                   |
| Unauthorized access attempt     | +30    | Accessing/downloading a document you don't own       |
| Excessive downloads             | +20    | 5+ downloads within 10 minutes                       |
| Rapid repeated actions          | +15    | 6+ actions within 30 seconds                         |

Risk levels: **0–30 LOW**, **31–60 MEDIUM**, **61–100 HIGH**.
Crossing into HIGH risk automatically creates a `SecurityAlert` and emits a
`securityAlert` Socket.IO event to connected admin dashboards.
All thresholds are configurable via `backend/.env`.

## 9. ML-based anomaly detection (Isolation Forest + One-Class SVM)

In addition to the rule-based risk engine (section 7), the system includes a
real **machine learning** anomaly detection layer, in `ml-service/`. This is
a separate Python microservice (FastAPI) that runs two unsupervised
classifiers side by side:

- **Isolation Forest** — isolates data points by random recursive splitting;
  anomalies need fewer splits to isolate, so they get an outlier score.
- **One-Class SVM** — learns a boundary around normal behavior in a kernel
  feature space; anything outside that boundary is flagged as an anomaly.

Both are trained **only on normal behavior** (that's the point of
unsupervised anomaly detection — you don't need labeled attack examples,
which matches reality: real attacks are rare and rarely labeled in advance).

### Features used

Every prediction is based on a 5-number snapshot of a user's recent activity,
computed live from MongoDB:

| Feature                  | Meaning                                         |
|---------------------------|--------------------------------------------------|
| `failed_logins_15m`       | failed logins in the last 15 minutes             |
| `downloads_10m`           | document downloads in the last 10 minutes         |
| `actions_30s`             | any actions in the last 30 seconds               |
| `unauthorized_attempts`   | unauthorized access attempts on record            |
| `hour_of_day`             | 0–23, when the activity happened                 |

### Running it

```bash
cd ml-service
pip install -r requirements.txt
python train_model.py          # trains + saves both models (prints accuracy report)
uvicorn main:app --host 0.0.0.0 --port 8001
```

Then set in `backend/.env`:
```
ML_SERVICE_URL=http://localhost:8001
```

The Node backend calls this service automatically after failed logins and
document downloads (`backend/services/riskService.js` → `evaluateMLAnomaly`).
If either model flags an anomaly, +20 risk points are added and an
`ML_ANOMALY_DETECTED` security alert is created — same real-time Socket.IO
pipeline as the rule-based alerts, so it shows up live on the dashboard too.

You can also trigger a classification manually from the API:
- `GET /api/risk/me/ml-status` — your own current classification
- `GET /api/risk/:userId/ml-status` — admin only, any user's classification

On the frontend, the **Risk Detection** page shows a live "Run ML check"
button per user (admin view) or an automatic ML panel (user view),
displaying each model's verdict and decision score.

### If the ML service isn't running

The integration fails soft — `evaluateMLAnomaly` catches the connection
error and simply skips the ML check, so the rest of the app (rule-based
risk scoring, login, uploads, everything else) keeps working normally.

### Explaining this in a viva

- **Why two models instead of one?** They make different assumptions about
  what "normal" looks like — Isolation Forest is tree-based and captures
  non-linear splits cheaply; One-Class SVM draws a smooth boundary in kernel
  space. Using both and flagging on agreement-by-either gives higher recall
  (catches more real anomalies) at the cost of some false positives, which
  is the right tradeoff for security monitoring — a human admin reviews and
  dismisses false alarms, but a missed real attack is costly.
- **What's the real-world application?** This maps directly onto **insider
  threat detection / user and entity behavior analytics (UEBA)** in
  enterprise document management, banking, healthcare records systems,
  or any environment handling sensitive files — systems like this are used
  alongside SIEM tools to catch compromised accounts or malicious insiders
  whose actions deviate from their normal baseline, even when no single
  action crosses an obvious rule threshold.
- **Why unsupervised?** In real deployments you have plenty of normal
  traffic and very few (if any) confirmed attack examples, so supervised
  classification isn't practical — anomaly detection models that only need
  "normal" data to train are the standard approach for this class of problem.

## 10. Notes

- Uploaded files are only ever served through the authenticated
  `/api/documents/:id/download` route — there is no static file server —
  so document access control can't be bypassed by guessing a URL.
- Passwords are hashed with bcrypt before being stored; the password field is
  never returned by the API (`select: false` + a `toJSON` transform).
- JWT tokens are stored in `localStorage` on the frontend and attached
  automatically to every API request. A `401` response anywhere in the app
  clears the session and redirects to `/login`.
